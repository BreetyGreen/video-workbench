# 跨平台剪映自动交付设计

日期：2026-08-31  
状态：用户已批准方向，等待书面规格复核  
目标平台：macOS（Apple Silicon 优先）与 Windows

## 1. 目标

把现有“生成 `draft.zip` 后由用户执行脚本”的半自动流程升级为本地闭环：启动前检测剪映，任务通过质量门禁后安全导入可编辑草稿，并尝试打开剪映。普通用户 clone 仓库后由 Codex 运行统一启动入口，不填写剪映路径或项目配置。

完成后，用户主流程是：

`clone → 告诉 Codex 启动 → 启动器检测剪映 → 上传素材并生成 → 质量门禁 → 自动导入剪映 → 打开剪映终审`

## 2. 成功标准

1. macOS 和 Windows 启动器都在服务启动前完成剪映应用与草稿目录检测。
2. 检测结果通过统一的本机运行时契约提供给控制面和设置页，包括平台、应用路径、草稿根目录、是否可写、是否需要用户处理和诊断原因。
3. 剪映未安装或尚未初始化时不阻止本地上传、剪辑、预览和 `draft.zip` 生成；界面只给出一个可执行动作：安装并至少打开一次剪映，然后点击重新检测。
4. 草稿结构与质量门禁通过后自动导入；导入不依赖人工批准状态。
5. 导入只创建新的项目目录，不覆盖、不扫描、不改写其他剪映项目。
6. 草稿内每条媒体路径在导入前完成平台路径重写并验证存在；任一媒体缺失时停止导入并保留原产物。
7. 导入成功后尝试打开已发现的剪映应用；打开失败不撤销已导入草稿。
8. 全新 clone 在无 `.env`、无云端 Key 的情况下通过 Windows、macOS CI 和隔离目录验证；真实客户端兼容性仍需在对应剪映版本上做一次人工打开验收。

## 3. 非目标与边界

- 不自动操作剪映时间线、导出按钮或发布按钮。
- 不承诺所有剪映版本都能无人值守导出成片；本功能只保证草稿生成、安全导入和尝试打开客户端。
- 不绕过 macOS 文件权限、Windows 目录权限、账号登录或剪映安全提示。
- 不把用户绝对路径、素材、草稿、密钥或本机运行时状态提交到 GitHub。
- 没有安装剪映不等于剪辑失败；系统必须保留 MP4、字幕、封面、质量报告和草稿包。

## 4. 架构

### 4.1 统一运行时检测

扩展现有 `doctor.py` 与 `app.platforms.jianying`，输出统一的 `JianyingRuntime`：

- `platform`：`darwin` 或 `windows`；
- `installed`：是否发现有效应用；
- `app_path`：本机应用路径；
- `draft_root`：经验证的本机草稿根目录；
- `draft_root_writable`：草稿根是否可写；
- `ready_for_auto_import`：应用、草稿根和权限是否满足；
- `needs_user_action`：`install_or_open_jianying`、`choose_draft_root`、`grant_folder_access` 或空值；
- `checked_at` 与可读诊断信息。

检测范围保持有界。macOS 使用 `mdfind`、`/Applications`、`~/Applications` 和有限用户目录；Windows 使用已知安装与草稿候选目录。检测不得遍历整个磁盘。

### 4.2 本机运行时清单

启动器把检测结果写入运行数据目录中的 `runtime/jianying.json`，使用临时文件加原子替换。该文件不包含密钥，由控制面只读。设置页与 `GET /api/local-runtime` 从同一清单读取，避免 Docker 内部把宿主 Windows 误判成 Linux。

Windows Docker 启动器把已验证的草稿根以只用于剪映交付的绑定挂载暴露给控制面，同时分别传入“容器可写路径”和“宿主机绝对路径”。未就绪时只挂载项目私有的空交付目录，并把自动导入标记为关闭。

macOS 原生运行直接使用本机草稿根，不经过 Docker。

### 4.3 安全导入服务

新增跨平台 `JianyingHandoffService`，统一完成：

1. 校验任务 UUID、`draft.zip`、质量报告和草稿清单；
2. 在项目私有 staging 目录解压，拒绝绝对路径、`..`、符号链接和多顶层目录；
3. 根据目标平台把包内 `/data/...` 或构建机路径重写为最终草稿目录中的 `assets` 绝对路径；
4. 验证 `draft_info.json` 及全部媒体路径；
5. 使用任务标题与短 UUID 生成唯一项目名；同名时追加后缀，永不覆盖；
6. 先写入临时目标目录，再原子改名为正式草稿目录；
7. 写入任务交付记录，包括目标、导入时间、路径重写数量、媒体验证结果和打开客户端结果。

Windows PowerShell 导入脚本改为调用同一导入契约或兼容包装器，保留手工重试入口，不再维护第二套规则。

### 4.4 自动触发与幂等

任务生成 `preview.mp4`、`draft.zip` 和质量报告后：

- 阻断项为零且 `ready_for_auto_import=true`：进入 `importing`，调用安全导入服务；成功后记录 `jianying_draft`/`imported`。
- 仅有质量警告：允许导入，并在结果页展示警告。
- 有阻断项：不导入，任务进入 `needs_attention`。
- 剪映未就绪：保留完成产物，记录 `handoff_waiting_for_jianying`；用户重新检测成功后自动重试。

以任务 ID 和草稿包 SHA-256 作为幂等键。重复启动、重复回调或用户点击重试都不得产生无限副本；只有草稿内容变化时才创建新版本。

## 5. 用户界面

首次进入或启动后的状态条显示以下之一：

- `剪映已就绪 · 完成后自动导入`
- `未检测到剪映 · 视频仍可生成`
- `已安装但未发现草稿目录 · 请打开一次剪映后重新检测`
- `草稿已导入 · 打开剪映`
- `导入失败 · 查看原因并重试`

现有审核页的“在剪映中导入草稿”不再是伪装成本机导入的 ZIP 下载链接。它改为显示真实交付状态；自动导入不可用时提供“重新检测”和“重试导入”，下载 ZIP 保留为恢复手段。

## 6. 错误处理

- 检测异常：记录诊断并降级，不阻断剪辑。
- 目录不可写：不请求管理员权限，提示用户授权实际草稿目录。
- ZIP 或 JSON 无效：停止导入，保留 staging 诊断，不触碰剪映目录。
- 媒体路径缺失：停止导入并列出缺失数量，不留下半成品正式草稿。
- 剪映打开失败：草稿仍标记为已导入，界面提供“再次打开”。
- 服务或机器重启：从交付记录恢复，重新核对幂等键，不重复导入。

## 7. 验证

### 自动测试

- macOS 与 Windows 应用、草稿根、多个候选、未初始化和不可写目录检测。
- 运行时清单原子写入与 Docker 宿主平台读取。
- 合法草稿导入、路径重写、媒体存在性验证和唯一命名。
- 路径穿越、符号链接、坏 ZIP、多顶层目录、缺媒体与同名目标拒绝。
- 质量通过自动导入、质量阻断不导入、剪映未就绪等待并在重新检测后重试。
- 重启与重复请求的幂等性。
- 设置页、工作台与任务结果页真实展示交付状态。
- fresh-clone 验证继续保证无 Key 本地主链可用。

### 真实机器验收

1. Apple Silicon Mac：clone 后只让 Codex 启动，确认检测剪映、生成任务、自动导入并打开应用。
2. Windows：Docker 模式确认启动前检测宿主剪映，自动挂载草稿根、导入、路径重写并打开应用。
3. 两个平台分别验证“未安装剪映”“安装但未打开”“正常就绪”三种状态。
4. 在当前正式剪映版本人工打开一个真实多素材、字幕、旁白草稿，确认时间线可编辑且媒体不离线。

## 8. 面向 clone 用户的完成定义

仓库只有在以下条件全部满足后，才能对外说明“clone 后可直接使用”：

- `AGENTS.md` 能指导 Codex 自动执行对应平台入口；
- 无云端 Key 时可完成本地视频生产；
- 启动前剪映检测已在 Windows/macOS CI 覆盖；
- 草稿自动导入链路在隔离目录端到端通过；
- fresh-clone 验证通过；
- README 清楚区分“自动导入草稿”和“不保证自动导出成片”；
- 至少一台真实 Windows 与一台 Apple Silicon Mac 完成客户端打开验收，或明确标注尚未完成的平台验证。
